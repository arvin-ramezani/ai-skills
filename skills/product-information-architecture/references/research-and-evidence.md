# Product IA Research and Evidence Protocol

Use this reference when information architecture depends on user behavior, domain rules, product evidence, support data, analytics, standards, regulation, or current system behavior.

## Start with a decision

Ask `What evidence would change this information-architecture decision?`

Examples:

- Do users think of orders under customers, stores, or operations?
- Which attributes distinguish two similarly named records?
- Which filters are repeatedly recreated in current workflows?
- Does a role need visibility or an explanation of restricted information?
- Would a relationship diagram improve onboarding, or are labels sufficient?

Stop when evidence is sufficient for the decision.

## Prefer evidence close to real work

Use, as appropriate:

1. Observed tasks, usability evidence, interviews, and contextual inquiry
2. Support, sales, training, search, and product analytics
3. Approved product policy, domain documentation, glossary, and current behavior
4. Legal, regulatory, standards, or platform sources
5. Comparable products as qualitative patterns, not proof of user need

Record source, date, role, product version, workflow context, and confidence. Distinguish source statements from inference.

## Maintain an evidence ledger

| Field | Requirement |
| --- | --- |
| Finding | Narrow, decision-relevant statement |
| Status | Confirmed / indicative / hypothesis / conflicting / unknown |
| Source | Direct link or named supplied artifact |
| Role/context | Applicable user and task |
| Product/version/date | Scope and freshness |
| Confidence | High / medium / low with reason |
| IA impact | Concept, term, object, relationship, navigation, list/detail, findability, visibility, localization, or visual requirement |

Do not convert the current UI or competitor pattern into a requirement without corroboration.

## Resolve conflicts deliberately

Common conflicts include:

- Policy terminology versus user language
- Backend entities versus user-facing objects
- Frequent user workflow versus organizational ownership
- Legacy navigation versus desired capability model
- Role expectations versus actual visibility policy
- Analytics frequency versus task criticality

Document the conflict, evidence on each side, chosen interpretation, owner, and validation need.

## Keep research output operational

Include findings that changed decisions, conflicting evidence, explicit inferences, remaining unknowns, and validation tasks. Exclude broad summaries that do not affect product information architecture.
